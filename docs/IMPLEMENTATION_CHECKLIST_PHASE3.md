# NexTrace Phase 3 — Implementation Checklist (Stages 1–11)

This checklist maps every Stage 1–11 requirement to the existing repository (`D:\Avishkar Nextrace\nextrace`), the required changes, the relevant tests, and the acceptance condition.

| Stage / Requirement | Existing Implementation | Required Changes | Relevant Tests | Acceptance Condition |
| :--- | :--- | :--- | :--- | :--- |
| **Stage 1A: Shared Resource Budgets** | `BudgetState` in `schemas.py` and `DiagnosticInterface` only track per-run model calls/tokens/cost without pre-dispatch reservation, safety margins, input-token estimation, or suite-wide ledger enforcement. | Add `SuiteAIBudgetLedger` (`nextrace_lab/budget_ledger.py`) shared across runs with per-run sublimits. Enforce finite nonnegative pricing validation when `max_cost_usd` is active, pre-dispatch conservative cost & token reservation (with documented 1.25x input safety margin), output-token capping to remaining allowance, reconciliation with actual usage, non-release of uncertain failed/interrupted calls, and `max_retries=0` on SDK clients so retries are strictly accounted for by NexTrace. | `tests/test_unit.py::test_suite_ai_budget_ledger_reservations_and_uncertain_failures` | Suite ledger rejects missing/invalid pricing when monetary cap is set, reserves before dispatch, caps output tokens, retains conservative charges on failed/uncertain calls, and stops subsequent calls when remaining budget cannot safely cover them. |
| **Stage 1B: Monotonic Deadlines** | `DiagnosticInterface` checks `elapsed_wall_time_ms > max_wall_time_ms` only at the start of `_begin_check`. | Add monotonic `DeadlineTracker` (`time.monotonic` / `perf_counter` or injected clock). Propagate `min(op_timeout, remaining_deadline_sec)` to HTTP requests, DB TCP/PostgreSQL operations, model calls, retry waits, and subprocesses. Reject operations that cannot fit remaining allowance (`min_required_ms`). Mark post-deadline completions as `TIME_BUDGET_EXHAUSTED` (never timely diagnosis). Bound recovery cleanup separately. | `tests/test_unit.py::test_deadline_propagation_and_overrun_rejection` | Operations do not start if remaining deadline is insufficient; any check or selector completing after deadline triggers `TIME_BUDGET_EXHAUSTED` and is recorded as a deadline overrun; recovery uses its own bounded timeout. |
| **Stage 1C: Failure Classification** | `DiagnosticOutcome` has `diagnosed, healthy, inconclusive`, and `experiment.py` treated `SELECTOR_OR_INFRASTRUCTURE_ERROR` reports as `execution_status="completed"`. | Add `UNKNOWN_CAUSE` outcome and explicit `RunFailureClassification` (`supported_diagnosis`, `honest_inconclusive`, `unknown_cause`, `selector_failure`, `diagnostic_tool_failure`, `setup_failure`, `recovery_failure`, `budget_exhaustion`, `deadline_exceeded`). Ensure `experiment.py` marks `SELECTOR_OR_INFRASTRUCTURE_ERROR` as `execution_status="failed"` (`failure_stage="diagnosis"`), preserves partial records, and keeps summary denominators explicit. | `tests/test_unit.py::test_selector_and_tool_failures_classified_as_execution_failures` | Selector or diagnostic-tool errors are never counted as ordinary diagnostic completions; partial records and failure classifications are saved in `run_outcome.json` and `summary.json`. |
| **Stage 1D: Fair Stopping** | `deterministic_checklist_v1` and `improved_checklist_v1` run all steps up to budget without early stopping. | Retain `deterministic_checklist_v1` and `improved_checklist_v1` unchanged for historical compatibility. Add `deterministic_checklist_early_stop_v1` and `improved_checklist_early_stop_v1` that apply the shared `EvidenceGate` after every check and stop immediately when sufficient evidence exists. | `tests/test_unit.py::test_fixed_checklist_early_stopping_parity` | Early-stopping fixed checklists stop as soon as `EvidenceGate` confirms a diagnosis or healthy state, using the exact same catalog, gate, and budget constraints as adaptive methods. |
| **Stage 1E: Execution Isolation Lock** | No cross-process lock between CLI and dashboard lab mutations. | Implement `LabExecutionLock` (`nextrace_lab/lab_lock.py`) using atomic file creation (`O_CREAT \| O_EXCL`) per `app_id` with PID, creation timestamp, and command metadata. Conservatively detect stale locks (only when recorded PID is dead AND lock age exceeds threshold) without killing unrelated processes. Wrap all fault, reset, and experiment mutations in CLI and dashboard. | `tests/test_unit.py::test_shared_lab_execution_lock_and_stale_recovery` | Concurrent lab mutations raise `LabLockContentionError`; stale locks from dead processes are safely recovered with an audit note. |
| **Stage 2: Formal Check Outcomes & Costs** | `check_catalog.py` defines basic check names, targets, and `cost_units=1`, without per-hypothesis expected outcome sets or freshness TTLs. | Upgrade `DiagnosticCheckDefinition` (`check_catalog.py`) with `version`, `evidence_source`, `outcome_categories`, set-valued `expected_outcomes_by_hypothesis` (with `reliability: "reliable" \| "uncertain"`), `estimated_duration_ms`, `cost_units` (positive, frozen from dev defaults), `freshness_ttl_sec`, and `side_effects`. Keep `system:other_or_unknown_cause` active. | `tests/test_unit.py::test_formal_check_catalog_set_valued_outcomes_and_costs` | Every check in both applications has a complete, frozen outcome & cost model with set-valued hypothesis expectations and zero references to private ground truth. |
| **Stage 3: Scored Selector (`scored_adaptive_v1`)** | Only branching `rule_adaptive_v1` exists. | Implement `ScoredAdaptiveSelector` (`nextrace_lab/scored_selector.py`) plus ablations (`scored_no_cost_v1`, `scored_no_avail_v1`). Compute explicit heuristic score: pair-separation ratio over remaining plausible hypotheses (or confirmation/refutation utility when 1 modeled hypothesis remains) × learned availability factor ÷ normalized positive cost, with deterministic tie-breaking and full per-step `ScoreBreakdown` trace. | `tests/test_unit.py::test_scored_selector_pair_separation_tie_breaking_and_ablations` | `scored_adaptive_v1` produces inspectable candidate scores, exclusion reasons, and tie-breaks deterministically, adapting to observed evidence without hidden policy metadata. |
| **Stage 4: Evidence Freshness & Conflicts** | `DiagnosticCheckRecord` has only `observed_at_utc`; no expiration, conflict detection, or historical-vs-current target separation. | Add `event_time_utc`, `collection_time_utc`, `observation_interval_start_utc/end_utc`, `freshness_ttl_sec`, and `is_expired_at(eval_time)` (using injected clock in tests). Preserve full observation history on repeat checks. Detect contradictory observations (`ConflictRecord`) and separate `window_diagnosis` (cause during incident window) from `current_health_status` (current state) so recovered incidents are never labeled "no fault" if historical failure evidence exists. | `tests/test_unit.py::test_evidence_freshness_expiration_conflicts_and_recovered_incident` | Expired live checks cannot support a current-state diagnosis; historical logs remain valid for the incident window; recovered incidents report historical cause/failure alongside current healthy state. |
| **Stage 5: Diagnostic Metrics** | Services expose `/internal/metrics`, but `DiagnosticInterface` has no registered tool to query them. | Add registered `get_service_metrics` check (`allowed_targets`: `gateway, order-service` in App 1; `api, inventory-service` in App 2) returning `request_count`, `failure_count`, `error_rate` (null when `request_count < min_samples`), `avg_duration_ms`, `max_duration_ms`, `dependency_failures`, `dependency_timeouts`, `collection_interval_sec`, and `resets_on_restart`. Add versioned evidence conditions `E4_METRICS_UNAVAILABLE` and `E5_METRICS_STALE` while preserving `E0–E3`. | `tests/test_unit.py::test_diagnostic_metrics_tool_min_samples_and_e4_e5_policies` | All methods can invoke `get_service_metrics`; zero/low samples are reported as `insufficient_samples` rather than `0.0` error rate; `E4/E5` policies are enforced. |
| **Stage 6: Challenging Incident Scenarios** | Only single static faults `fault_a..fault_f` exist. | Add 5 challenging scenarios in `controller.py` & `hypotheses.py`:<br>1. `challenging_recovery_mid_run` (fault active during incident workload, recovers via deterministic hook after 1st check)<br>2. `challenging_diag_endpoint_failure` (`/internal/diagnostics/db-config` fails HTTP 500 while order traffic is healthy 201)<br>3. `challenging_historical_logs_healthy_now` (failure logs in incident window, services currently healthy)<br>4. `challenging_unknown_app_error` (unmodeled internal serialization error in `order-service` while all dependencies are healthy -> must conclude `unknown_cause` / `system:other_or_unknown_cause`)<br>5. `multi_fault_a_and_b` (simultaneous `fault_a` + `fault_b`, scored with cause-set precision, recall, and exact-set match). | `tests/test_integration.py::test_challenging_and_multi_fault_scenarios` | All 5 challenging scenarios inject/reset cleanly, preserve persisted data, and verify recovered-state, unknown-cause, and multi-cause set scoring. |
| **Stage 7: AI Selection & Prompt-Injection Defense** | `ai_selector.py` has basic regex neutralization and mock tests. | Upgrade `ai_selector.py` to use `SuiteAIBudgetLedger`, monotonic deadlines, temporal context in observations, and architectural boundary enforcement (even if an adversarial log tricks the model into proposing a fabricated check, citing bogus evidence, or claiming a healthy service is faulty, the catalog validator and `EvidenceGate` block it). Keep live AI status "not run" unless user-authorized credentials + `--max-cost-usd` are supplied. | `tests/test_unit.py::test_ai_selector_adversarial_log_injection_blocked_by_architecture` | Adversarial telemetry cannot bypass tool validation or `EvidenceGate`; failed model calls charge the shared ledger; missing credentials fail fast without silent fallback. |
| **Stage 8: Second Application (`inventory_app`)** | Only `orders_app` (`gateway -> order-service -> database`) exists. | Add isolated second application `inventory_app` (`api [18010] -> inventory-service [18011] -> database [15433] + cache [16379]`). Implement standalone TCP cache server (`nextrace_lab/local_cache_server.py`, labeled `local_tcp_cache_substitute` locally vs Redis in Docker) with documented `require_cache` vs `fallback_slow_db` behavior. Refactor reusable engine (`AppAdapterProtocol` in `nextrace_lab/app_adapter.py`) and add scenarios: `inv_healthy`, `inv_service_unavailable`, `inv_db_unavailable`, `inv_cache_unavailable`. | `tests/test_integration.py::test_second_application_inventory_lab_and_engine_reuse` | `inventory_app` runs on isolated ports/files, reuses `run_adaptive_engine`, `ScoredAdaptiveSelector`, and `EvidenceGate`, and documents exact application-specific additions vs shared engine code. |
| **Stage 9: Fair Evaluation Protocol** | `experiment.py` runs sequential methods without seed counterbalancing or frozen protocol metadata. | Save versioned protocol (`docs/EVALUATION_PROTOCOL.md` & `nextrace_lab/protocol.py`), counterbalance/randomize method execution order per cell using recorded `seed`, reset app/cache state between trials, separate `smoke`, `dev`, `held_out`, `stress_multi`, `app2_inventory`, and `paid_ai` suites, and report primary/secondary/set metrics with per-scenario sample sizes. | `tests/test_unit.py::test_counterbalanced_evaluation_protocol_and_multi_fault_metrics` | Experiment suites record frozen protocol hash, counterbalance method order, and report all primary, secondary, and multi-fault set metrics. |
| **Stage 10 & 11: Dashboard, Tests & Documentation** | `dashboard.py` shows App 1 only without score breakdowns, freshness/conflict badges, or lock awareness. | Upgrade `dashboard.py` to select application (`orders_app` vs `inventory_app`), honor `LabExecutionLock`, and display `window_diagnosis` vs `current_health_status`, check score tables, freshness/conflict badges, budget ledger state, and failure classifications. Update `README.md`, `docs/SPECIFICATION.md`, `docs/EVALUATION_PROTOCOL.md`, and `docs/VERIFICATION_REPORT.md`. | Full `pytest` suite (`test_unit.py` + `test_integration.py`) | All unit and live integration tests pass, comparative suites execute and save durable artifacts, and documentation matches actual verified results. |
